Ingestion (offline prep) Retrieval + Generation (live) Ongoing maintenance

⚙️ Ingestion — built ahead of time

1. Documents (collect sources)

PurposeGather every source the assistant should be able to answer from.
Usually doneConnect to SharePoint, Confluence, Drive, databases, ticketing systems; pull the files/records in scope.
PM watch-outsGetting access & credentials from other teams is often the slowest part. Agree which sources are in/out of scope up front.
ProblemsAccess delays, surprise formats, huge volume, duplicate or already-outdated documents.

2. Extract text (parsing)

PurposeConvert every file into plain text the AI can actually read.
Usually donePDF/Word/HTML parsers; OCR for scans/images; special handling for tables and layout.
PM watch-outsTest on your messiest real documents early — this step is routinely underestimated. Budget time for it.
ProblemsScrambled tables, OCR errors, lost charts/images, junk from headers & footers.

3. Clean

PurposeRemove noise so later search isn't polluted by junk.
Usually doneStrip boilerplate/repeated headers, fix encoding, drop empty sections, de-duplicate.
PM watch-outsDefine cleaning rules — don't let it get so aggressive it deletes meaningful content.
ProblemsGarbage text lowers accuracy; over-cleaning removes useful info.

4. Chunk

PurposeSplit documents into retrievable, context-sized pieces.
Usually donePick chunk size + overlap; split by section/paragraph (smart) or fixed length (naive).
PM watch-outsThis is the biggest lever on answer quality. Expect iteration — there's no single "right" setting.
ProblemsToo big = noisy answers; too small = lost context; one idea split across chunks.

5. Metadata tagging

PurposeAttach labels for filtering, security, and citations.
Usually doneTag source, date, version, page, department, and access permissions.
PM watch-outsCapture permissions during ingestion — this is what enforces who-can-see-what later. Retrofitting is painful.
ProblemsMissing permissions → confidential leaks; no citations; can't filter by recency/department.

6. Embed chunks

PurposeTurn each chunk into a vector that captures its meaning, so it's searchable.
Usually doneRun all chunks through the chosen embedding model (API or self-hosted).
PM watch-outsPick the model early — switching later means re-embedding everything. Cost scales with volume; check privacy if using an API.
ProblemsVendor lock-in, data leaving your network, cost surprises on large sets, slow batch jobs.

7. Store / index (vector DB)

PurposeSave vectors + text + metadata so they can be searched in milliseconds.
Usually doneLoad into a vector database (Pinecone, Weaviate, pgvector, Chroma) and build the index.
PM watch-outsDB choice is coupled to the embedding's vector size. Decide cloud vs on-prem (compliance) and watch scaling cost.
ProblemsPerformance/cost growth at volume; index drift if not maintained.

♻️ Re-indexing (ongoing)

PurposeKeep the knowledge base current as documents change.
Usually doneScheduled or event-driven refresh of added/changed/removed docs.
PM watch-outsDecide frequency (real-time vs nightly) and assign an owner — it's a living pipeline, not one-off.
ProblemsStale data → confidently wrong answers; deleted docs still answerable; high refresh cost.

🔎 Retrieval + Generation — live, when a user asks

8. User query

PurposeCapture what the user actually wants to know.
Usually doneReceive the question via chat/search UI; optionally rewrite/expand vague queries.
PM watch-outsShort/ambiguous questions retrieve poorly — consider guiding users or auto-rewriting.
ProblemsAmbiguous or multi-part questions; off-topic questions outside the docs.

9. Embed query

PurposeConvert the question into the same vector space as the chunks.
Usually doneEmbed the query with the same model used at ingestion.
PM watch-outsDocs and queries must use the identical embedding model — non-negotiable.
ProblemsModel mismatch → irrelevant results, even if everything else is correct.

10. Retrieve top-k

PurposeFind the chunks most relevant to the question.
Usually doneSimilarity search in the vector DB returns the top-k chunks; often with metadata filters or hybrid (keyword + semantic) search.
PM watch-outsApply permission filters here. Tune k. This step makes or breaks answer quality.
ProblemsMisses the right doc → wrong answer; pulls irrelevant chunks; permission bypass if filters are wrong.

11. Rerank (optional)

PurposeRe-sort retrieved chunks so the best ones go first.
Usually doneA reranker model re-scores chunk-vs-query relevance; keep the top few.
PM watch-outsOften a big quality win, but adds cost & latency — evaluate whether it's needed.
ProblemsExtra latency/cost; another model dependency; commonly skipped early, then needed later.

12. Augment prompt

PurposeCombine question + retrieved chunks + instructions into the LLM's input.
Usually doneAssemble a prompt template that fits the context window and tells the model to "answer only from the provided context."
PM watch-outsContext window limits how much fits; prompt design strongly affects grounding & tone.
ProblemsToo much context = truncation/cost; weak instructions = hallucination; wrong template = sources ignored.

13. LLM generates

PurposeProduce the final answer from the provided context.
Usually doneSend the prompt to an LLM (Claude/GPT/Gemini/etc.); stream the answer back.
PM watch-outsModel choice is a cost vs quality vs latency vs privacy trade-off — same buy-vs-host questions as embeddings.
ProblemsHallucination despite context; per-call cost; latency; vendor rate limits/outages.

14. Answer + citations

PurposeDeliver a grounded answer the user can trust and verify.
Usually doneReturn the answer with source links; handle "I don't know" gracefully; collect user feedback.
PM watch-outsCitations build trust & enable verification. Define behavior when no good answer exists; add a human-in-the-loop feedback button.
ProblemsWrong/fake citations; over-confident wrong answers; no feedback loop = no improvement over time.
